File transfer

DECIMEN sends files from one device to another using only a screen and a camera. The payload travels as animated QR codes — fountain coded, AES-256-GCM encrypted, compressed — with no Wi-Fi, Bluetooth, USB or cloud account in the path.

How it works
01 / ENCODE
Fountain coding

The file is sliced into blocks, then LT-encoded into a theoretically infinite stream of distinct coded frames. The receiver can reconstruct the original from any ~1.18× overhead of frames — in any order, with any gaps.

02 / SECURE
Key QR + encryption

Before the data stream starts, the sender shows a key QR code encoding a 32-byte AES-256-GCM session key. The receiver scans it once. All data frames are encrypted; the auth tag catches any tampering or bit-flip in transit.

03 / TRANSMIT
Animated QR grid

The sender renders up to a 4×4 grid of QR codes per screen frame — each cell carries a different fountain frame. zxing-wasm decodes all visible symbols from one camera capture in a single worker pass.

04 / RECEIVE
Decode + verify

Once the decoder has enough unique frames, LT peeling reconstructs the payload. FNV-1a hash is verified over the encrypted blob, then AES-GCM decrypts and the file downloads with the original filename.

How it looks in practice

The sender renders a 2×2 grid of animated QR codes. Hold your phone's camera up to the screen — no app, no pairing, no network required.

What was built — six phases
0Foundation
Fountain codec + raw QR stream

Core LT fountain encoder and decoder (splitmix32 PRNG, robust-soliton degree distribution), frame packing with a 20-byte self-describing header, and the sender/receiver UI shell. Multi-page Vite build, TypeScript, ESLint, Vitest CI from day one.

Protocol v0 · Raw payload
1Compress
gzip compression via CompressionStreams

Payload is gzip-compressed before fountain-splitting using the browser-native Compression Streams API. No dependencies added. FNV-1a hash recorded over the compressed bytes so the receiver can verify integrity before decryption.

Protocol v1 · ~30-40% smaller on typical files
2Encrypt
AES-256-GCM end-to-end encryption

A 32-byte AES-256-GCM session key is generated fresh per transfer, encoded into a separate key QR code shown before the data stream, and used to encrypt the entire compressed payload. The 12-byte IV is random per encryption; the 16-byte auth tag travels with the ciphertext. SubtleCrypto throughout — no third-party crypto library.

Protocol v2 · AES-256-GCM · SubtleCrypto
3Grid
Multi-QR grid — ~10× throughput gain

The sender renders a 1×1, 2×2, 3×3, or 4×4 grid of independent QR codes per screen frame, each carrying a different fountain frame. zxing-wasm's maxNumberOfSymbols decodes all cells in a single camera capture. Device-tested at 44 KB/s on 2×2, ~10× over the single-QR baseline. The key QR remains a single code shown once.

44 KB/s measured · Real device verified
4Files
Arbitrary file support + multi-file bundles

A DCMN bundle format wraps one or more files (filename, MIME type, content) inside the encrypted payload — metadata is protected by AES-GCM along with the data. The receiver unbundles and offers typed downloads for each file, with image preview for image/* files. Sender UI now accepts any file via a standard file picker.

Any file type · Multi-file · DCMN bundle format
5Resume
Resumable sessions via IndexedDB

If the receiver page is reloaded mid-transfer (accidental navigation, phone lock), it offers to resume from the last saved snapshot rather than restarting. The LT decoder state (solved blocks + seen sequence numbers) and AES key are persisted to IndexedDB, throttled to every ~2 s. Device-tested: interrupted at 56% (272 KB of 484 KB), resumed, completed correctly.

56% resume tested · IDB persistence · Key cleared on finish
6Harden
Security hardening + QA pass

parseFrame now enforces upper bounds: blockLen ≤ 2953 (QR V40 physical max) and totalLen ≤ 500 MB. Bundle manifest bounds prevent a malicious fileCount or oversized filename from spinning before truncation checks fire. Full DOM XSS audit confirmed all bundle-derived strings go through textContent. End-to-end pipeline integration test added covering every pure layer.

125 tests · 0 vulnerabilities (npm audit)
Protocol v2 wire format. Every QR code carries a 20-byte self-describing header: magic(1) · version(1) · sessionId(2) · seq(4) · k(2) · blockLen(2) · totalLen(4) · fnv(4), followed by blockLen bytes of fountain-coded encrypted payload. The receiver locks onto a new session on any frame — no handshake, no pairing, no negotiation. Sender and receiver only need to agree on grid density — set them both to the same value in Settings.
How to use it
Sender — laptop / desktop
  1. Open Send below in Chrome or Firefox
  2. Choose a file (or drag one in)
  3. Set grid density to 2×2 for speed
  4. Point your phone camera at the key QR first
  5. Then point at the flickering data grid
  6. Keep screen at max brightness
Open sender →
Receiver — phone / tablet
  1. Open Receive below on your phone
  2. Match grid density to the sender's setting
  3. Tap Start camera
  4. Scan the key QR (banner turns green when received)
  5. Steady the phone — wait for the progress bar
  6. Download link appears when complete
Open receiver →
